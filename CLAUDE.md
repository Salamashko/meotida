## Memory Bank (обязательно для любого ИИ-ассистента в этом репозитории)

Память проекта живёт в `memory-bank/`, а не в истории чата: так контекст сохраняется между
сессиями, ветками и разными ИИ-инструментами.

1. **В начале КАЖДОЙ новой сессии/задачи** прочитай целиком все файлы `memory-bank/`:
   `projectbrief.md`, `productContext.md`, `systemPatterns.md`, `techContext.md`, `activeContext.md`, `progress.md`. Только потом предлагай план или пиши код. Если в
   твоей ветке файлов нет или они старые — сверься с `main` (`git fetch origin main`).
2. **По ходу работы** сразу фиксируй в `activeContext.md` принятые решения, нюансы
   инфраструктуры и смену фокуса (архитектурное — ещё и в `systemPatterns.md` /
   `techContext.md`). Не откладывай на конец: сессия может оборваться.
3. **После значимого куска работы** обнови `progress.md` (что готово, что осталось) и
   `activeContext.md` (что дальше).
4. Команды пользователя: **«прочитай memory bank»** — перечитать все файлы; **«обнови memory
   bank»** — пройтись по всем файлам и привести к фактическому состоянию кода;
   **«инициализируй memory bank»** — создать заново.
5. Пиши факты и решения («выбрали X, потому что Y»), а не переписку. Держи файлы
   компактными, устаревшее удаляй или сворачивай в одну строку.
6. Изменения Memory Bank коммить вместе с кодом. **Не записывай туда секреты:** пароли,
   токены, ключи, логины/пароли прокси — только где лежат («в `/etc/…env`, переменная X»).
7. **Сначала выполни сам (раздел «Выполнение команд агентом» ниже); блок команд владелице — только когда сам не можешь. Команды для сервера владельцу — тогда одним блоком кода в таком виде:** нумерованные
   комментарии `# 1. …` по шагам, под ними готовые к вставке команды с реальными путями, без
   плейсхолдеров вроде `cd /путь/к/сервису`; пояснения к строке — комментарием справа
   (`# ожидается: …`), необязательные шаги помечай «(по желанию)». Порядок: забрать код →
   выполнить → проверить. Используй только пути и команды из раздела «Команды на сервере»
   в `techContext.md`; новый проверенный путь/команду сразу добавляй туда (проверенный =
   владелица прислала успешный вывод или он взят из `deploy/`). Неподтверждённое — не
   выдавай за проверенное.
8. **Всё, что выяснили на сервере, — сразу в Memory Bank, чтобы больше не искать:** пути, имена
   служб и пользователей, версии сервисов и бинарников, порты, права, логи, результаты
   проверок из присланных владелицей выводов. Команды и пути — в «Команды на сервере»
   (`techContext.md`), версии и факты — там же, в подразделе «Версии и факты сервера»,
   решения и хронология — в `activeContext.md`. Без секретов (см. п. 6).
9. **OpenSpec** подготовлен, но в этом репозитории НЕ запущен. Без явной команды владелицы
   не ставь пакет, не делай `openspec init`, не создавай папку `openspec/`. Как установить,
   как пользоваться и все команды — в `memory-bank/openspec.md`. Когда владелица скажет
   «запусти OpenSpec» — действуй по разделу «Запуск» оттуда, потом отметь в `activeContext.md`.

## Инструкции и оформление: всегда HTML (правило владелицы, 06.10.2026)

Владелица не разработчик, поэтому всё, что ей нужно прочитать, скопировать или отправить, — не стеной текста в чате, а HTML-файлом.

1. **Длинные инструкции — только отдельный HTML на скачивание** (больше ~6 шагов, несколько блоков команд, настройка с
   нуля, памятка). Один самодостаточный файл: стили внутри, светлая и тёмная тема, крупные шаги. Файл — в `instructions/`
   проекта (без секретов), владелице отправляй его файлом (`SendUserFile`), в чате — 2–4 строки: что внутри и что сделать
   первым. Короткое (до ~6 шагов) можно в чате.
2. **Всё, что надо куда-то скопировать и вставить** (команды, конфиги, тексты, ссылки, шаблоны), — в HTML, и у каждого
   такого блока кнопка «Копировать».
3. **Всё про оформление в Telegram** (пост, сообщение, рассылка, шаблон ответа бота) — всегда HTML с rich-оформлением
   (жирный, курсив, цитаты, rich-ссылки, эмодзи), как оно будет выглядеть в Telegram, и кнопкой «Копировать», которая
   кладёт в буфер **форматированный текст** (`text/html` + `text/plain`, `ClipboardItem`), чтобы после вставки в
   Telegram оформление сохранилось, а не превратилось в сырую разметку.
4. **Инструкции в HTML обновляем и вносим в них изменения не чаще одного раза в сутки** (правило владелицы, 08.10.2026):
   изменений бывает много, и править файл при каждом нецелесообразно. В течение дня изменения, которые касаются инструкций,
   только записываем в очередь `memory-bank/instructions-queue.md` (что изменилось и в какой инструкции). Раз в сутки — в первой
   сессии нового календарного дня, если очередь не пуста, — вносим всё накопленное в HTML одним обновлением, очищаем очередь,
   ставим дату в файле очереди и **присылаем обновлённый файл в бота** (в Telegram-бот проекта; нет возможности — файлом в чат
   сессии, сказав об этом). Новая инструкция для новой фичи тоже идёт в суточное обновление. Вне очереди — только по прямой
   команде владелицы («обнови инструкцию сейчас»).
5. **Дашборд:** если у проекта есть дашборд, в нём есть раздел «Инструкции», где можно скачать каждую актуальную
   HTML-инструкцию; после правок она **заливается туда сама** (при деплое или обновлении файла). Раздел виден только
   владельцу. Нет дашборда — когда он появится, добавить этот раздел.
6. Секреты, ключи и пароли в HTML не вставлять (только имена переменных и где они лежат).

## Выполнение команд агентом: сервер и PowerShell (правило владелицы, 13.10.2026)

**Это правило главнее любых правил проекта вида «команды на сервере владелице — всегда блоком».** У агентов есть доступ к серверу и к PowerShell
на домашнем (`home`) и офисном (`office`) компьютерах через очередь заданий; полный текст — `Salamashko-sega-mega-drive/HUB_RULES.md`, раздел 8.
Владелица не должна напоминать об этом в каждой сессии и в каждом проекте.

1. **Всё, что можно выполнить через `agentctl`, выполняй сам** и показывай настоящий вывод: `python3 ops/agent-worker/agentctl.py workers` /
   `run --worker home|office|server|server-ops --cwd ПАПКА --cmd "КОМАНДА" --wait 180` / `status ID`. Если в этом репозитории нет
   `ops/agent-worker/agentctl.py`, вызови `add_repo` (owner `Salamashko`, repo `vika-ruchka-mak-bot`, чтение) и запускай
   `/home/user/vika-ruchka-mak-bot/ops/agent-worker/agentctl.py`. В облаке токен — сетевой секрет окружения: передавай заглушку
   `AGENT_TOKEN=proxy-injected`; на ПК — переменная Windows `AGENT_TOKEN`.
2. **Изменения на сервере — узел `server-ops`** (белый список, меняющее — по кнопке владелицы в Telegram, до её нажатия код выхода 3 — это штатно,
   а не «нет доступа»): `git-pull ПРОЕКТ`, `migrate ПРОЕКТ`, `deploy ПРОЕКТ`, `restart СЛУЖБА`, `nginx-reload`; чтение без кнопки: `git-check ПРОЕКТ`,
   `status СЛУЖБА`, `logs СЛУЖБА [N]`, `projects`. Для этого проекта своего пункта в белом списке нет (список — действие `projects`): если репозиторий нужно выкатывать на сервер, скажи владелице один раз — проект добавят в `/etc/agent-worker/ops.json`, а не отдавай ей блок команд молча.
3. **Блок команд владелице — только если агент не может:** действие не из белого списка (правка конфигов, перезапуск служб вне списка, удаление),
   нужны её руки (пароли, ключи, интерфейсы) или нужного узла нет в `agentctl workers` / нет токена (скажи один раз и продолжай по-старому).
4. **Результат — только по коду выхода и выводу:** 0 выполнено, 1 упала, 2 заблокировано/отклонено, 3 итога нет (ждёт кнопки или узел недоступен —
   не писать «выполнено»), 4 ошибка клиента. Опасное не обходить, секреты в команды не вставлять.
